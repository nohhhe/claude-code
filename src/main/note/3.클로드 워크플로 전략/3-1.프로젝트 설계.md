3-1.프로젝트 설계
=========================
## ⭕ 개요
클로드 코드를 활용해 프로젝트를 계획하는 방법을 다룹니다.
- 프로젝트 아키텍처 설계 지원
- 기술 스택 후보 검증 및 선택
- 프로젝트 구조 설계 및 보일러플레이트 생성
- WBS 작성
- 에상 일정 및 리소스 산정

## ⭕ 프로젝트 아키텍처 설계
### ◉ 아키텍처 다이어그램 생성
아키텍처 다이어그램은 시스템의 전체 구조를 한 눈에 보여주는 핵심 도구 입니다.

클로드 코드는 머메이드와 같은 텍스트 기반 다이어그램 언어를 자동으로 생성해주기 때문에, 복잡한 문법을 직접 다룰 필요 없이 요구사항에만 집중할 수 있습니다.

### ◉ 기술 스택 검증
클로드 코드가 각 기술 스택 간의 호환성을 체크하고, 타입스크립트 버전을 통일해야 할 필요성, 도커의 이미지 크기 최적화 방법, 쿠버네티스에서의 상태 관리 전략 등 실무에서 놓치기 쉬운 세부사항들까지 짚어줍니다.
- 기술 간 호환성 문제
- 버전 충돌 가능성
- 팀의 학습 곡선

## ⭕ 프로젝트 구조 설계
### ◉ 디렉터리 구조 생성
프로젝트 디렉터리 구조는 코드의 유지보수성과 확장성을 좌우하는 핵심 설계 요소입니다.

클로드 코드는 축전된 다양한 프로젝트 사례와 패턴을 기반으로, 프로젝트의 유형과 규모에 적합한 디렉터리 구조를 제안합니다.
특히 모노레포처럼 복잡한 환경에서도 일관성과 확장성을 유지할 수 있는 구조적 원칙을 적용하여 장기적인 운영 효율성을 높여줍니다.

### ◉ 설정 파일 자동 생성
프로젝트의 개발 환경 설정은 팀의 코드 품질과 일관성을 유지하는데 핵심적인 역할을 합니다.
이러한 설정들을 매번 수동으로 작성할 필요 없이 클로드 코드는 베스트프렉티스를 반영한 설정 파일들을 한번에 생성해줍니다.

## ⭕ WBS 작성
### ◉ 자동 WBS 생성
WBS는 프로젝트의 전체 범위를 관리 가능한 단위로 나누는 기본 도구입니다. 작업을 충분히 세분화하지 않으면 일정 예측이 어긋나거나 리소스 배분이 불균형해지는 문제를 발생할 수 있습니다.
- 시간 추정: 단순 추측이 아니라, 평균적인 난이도와 포함되는 세부 작업을 고려한 값
- 의존성 관리: 선행 작업을 명시해 어떤 작업은 병렬로 진행 가능하고, 어떤 것은 순차적으로 이어져야 하는지 구분할 수 있습니다.
- 리소스 분배: 개발자들의 작업이 균형 있게 배분되어, 특정 인력이 놀거나 과부하되지 않도록 설계합니다.
- 버퍼 고려: 실제 실행에서는 일정의 20~30%를 여유로 잡아 예상치 못한 변수에 대응할 수 있습니다.

### ◉ 타겟 관리 시스템과의 연동
WBS는 자체로도 유용하지만 협업에서 티켓 관리 도구와 연결되어야 효과를 발휘합니다. 깃허브, 지라, 아사나, 트렐로 같은 툴을 클로드 코드를 활용하면 WBS를 바탕으로 티켓 생성 요청을 자동화할 수 있습니다.
- 반복 업무 감소: 수십 개 작업을 하나씩 수동으로 입력하는 부담을 줄임
- 일관성 확보: 티켓 제목, 설명, 담당자, 예상 시간 등이 동일한 기준으로 생성됨
- 연동 유연성: 깃허브, 지라, 리니어 등 팀이 선호하는 시스템에 맞춰 적용 가능

## ⭕ 리스크 분석과 대응 계획
### ◉ 기술적 리스크 식별
프로젝트를 시작할 떄 가장 중요한 일 중 하나가 리스크 분석입니다. 초기에는 순조롭게 진행되더라도 나중에 예기치 못한 기술적 문제가 발생하면 수정 비용이 매우 커지기 때문입니다.
특히 확장성, 성능, 보안과 같은 비기능적 요구사항은 초기에 고려하지 않으면 뒤늦게 큰 장애 요인으로 돌아올 수 있습니다.

## ⭕ 프로젝트 문서 템플리 생성
### ◉ README 템플릿 생성
README는 프로젝트의 첫인상을 결정하는 핵심 문서입니다. 잘 작성된 README는 프로젝트를 처음 접하는 개발자가 빠르게 이해하고 기여할 수 있도록 도와줍니다.

클로드는 프로젝트의 특성과 규모를 고려해 맞춤형 README 템플릿을 생성합니다. 단순한 형식 제공이 아니라, 실제로 필요한 항목(설치 가이드, 한경 변수, 트러블 슈팅, API 문서 링크 등)을 빠짐없이 포함시켜 실무에서 곧바로 활용 가능한 문서를 만듭니다.

### ◉ ADR 작성
아키텍처 결정은 프로젝트의 장기적인 방향에 큰 영향을 미칩니다. 의사결정의 맥락을 기록하지 않으면 나중에 확인이 어렵고 이는 불필요한 리팩토링이나 기술 부채로 이어질 수 있습니다.
ADR은 이러한 중요한 결정을 체계적으로 기록하는 방법입니다.

#### ❗️ 구두로 논의하거나 그런 부분들을 클로드에게 요청하여 ADR 작성해서 컨플로 관리하면 도움이 되지 않을까 생각

### ◉ README와 ADR의 차이
- README는 외부인(새 기여자, 새 팀원)을 위한 가이드 역할
- ADR은 내부 팀을 위한 기억과 기준점 역할
